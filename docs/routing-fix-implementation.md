# Routing and clarification implementation

Implemented 2026-10-12 against [the current-request plan](routing-fix-plan.md). The static app still uses native Prompt API/WebMCP, relative modules and IndexedDB v2 with no build or new dependency.

## What changed

`request-policy.js` owns current-only facts and finite semantic steps. Strong anchors bypass bridge route inference and expose only one constrained argument schema. Native declarations and the host's finalized-batch validation use the same step constraints. Literal data is masked during operation classification. A success or verified no-op fulfills its step once; no new route is inferred after all requested steps are done. A strictly empty mind-dump introduction attaches to its following actual capture rather than creating another step. Header-only or unsupported following work asks what to capture; distinct capture clauses remain separate. Unknown actionable wording retains bounded model routing; unsupported or contradictory compounds clarify before effects.

Exact context edits allow only the selected Task reference and `patch.context`. Singleton choices, host equality and saved-result checks preserve case, whitespace, @ markers, slashes and explicit clearing. ID-like literals use a private exact-value restoration after a readable sentinel choice. Other patch fields, omitted values, substituted contexts and unrelated targets are rejected despite chat grants. Approval displays old/new context.

Task statuses, moves and review transitions are distinct steps. A preservation clause creates no Task write. Compounded item work defers review progress to a new human message. Saved review state is read at admission; if the displayed current position changed, the app refreshes it and requests confirmation. Original-step binding is checked again at callback entry before permission and by the existing IndexedDB transition fence.

Immediate current-turn restatements such as a waiting statement followed by “Set that task to Waiting For” share their grounded subject and collapse identical effects. Independent fields remain separate steps; intervening preservation, negative or unsupported clauses clear that subject. Capture-it/them restatements following supplied thoughts similarly stay one capture. Completed mind-dump narration supplies no capture authority. Existing Project names containing “new” or “new Project named” remain existing destinations; positive new-Project syntax outside known names selects creation. The app no longer supplies an unrestricted whole-message new-title preference before planning.

Clarification is grounded and tool-free. Only an affirmative move with unique Task choices creates an in-memory pending destination descriptor. A fresh natural Project/Inbox answer revalidates records and title uniqueness before normal permission; negated answers, duplicate/deleted/stale choices and unrelated work cannot silently choose a parent. Stop, New chat and reload discard this authority. A pure question never creates latent move authority.

The plan bound is eighteen requested steps, rather than the initial suggested six, so explicit work can exercise the existing six-dispatch segment/Continue mechanism. Continue preserves the original aliases, plan position, receipts and totals. Later independent fields on one Task advance only from immutable committed records, with fresh equality checks; conflicting same-field requests clarify first. New records remain unavailable as general references until a fresh turn.

UI-generated weekly guidance now renders the trusted current step's instruction/question without inference, reads or navigation tools. This removes invented `weekly-review` filters and the follow-up read cycle. The service worker advances to v7 and precaches the new module while retaining subpath, HTTP-cache and offline checks.

## Limits

The finite host prevents post-success invented operations for recognized requests; it does not solve unrestricted English interpretation. Context assignment requires a clear literal boundary. Ambiguous wording, duplicate workflow titles or unparsed compound clauses may need a fresh explicit clarification. Proposed arguments still require ordinary approval; no automatic correction/retry runs after a dispatched error. Optional typed native proposal inference still requires a real-browser canary and is distinct from scripted native transport tests.
