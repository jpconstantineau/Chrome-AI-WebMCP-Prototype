### Imperative source traces

**Pizza.** Registration uses `document.modelContext` and explicitly exposes tools to selected localhost origins and `chrome.dev`. Size can be explicit or inferred from guest count. Topping additions constrain identifiers and clamp count; removals can remove one or all of a kind. These callbacks share normal UI functions. Results are human-readable strings; an invalid style returns an “Invalid…” string rather than a structured failure. This is illustrative code, not a general success/error contract. The useful local adaptation is a bounded, validated capability with a factual result; copy neither its exposure origins nor its loose error classification. [Pizza source, lines 204–380](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/demos/pizza-maker/script.js#L204-L380).

**Maze.** `ToolRegistry` aborts the prior registration controller before replacing the catalog for intro, gameplay, or game-over state. Its `window.gameTools` helper directly calls the current callback, making it useful internally but bypassing browser-mediated `executeTool`. The opt-in `?eval_tool` exposes code execution through a sandboxed opaque-origin iframe and worker, with allowlisted game tools, denied network APIs, CSP, timeout, and cleanup. That is a separate attack surface, not a reason to expose arbitrary JavaScript in the list manager. Future prototype work should favor existing structured workflow operations and explicit state eligibility. [Registry, lines 53–134](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/demos/webmcp-maze/src/webmcp/ToolRegistry.ts#L53-L134); [EvalTool sandbox and bridge, lines 6–33 and 164–202](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/demos/webmcp-maze/src/webmcp/tools/EvalTool.ts#L6-L33).

**Doors.** Hallway forms navigate into distinct documents. Each destination then owns different imperative tools and a return tool. The magic page can use either an imperative return callback or form declaration. An agent must rediscover after navigation; an old descriptor or assumed catalog cannot represent the next page. The prototype's own-page origin/window filter is a narrower design, while current selection, saved review state, and eligibility still need refreshing. [Hallway forms](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/demos/doors/index.html#L88-L99); [magic variant](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/demos/doors/magic.html#L35-L72); [prototype discovery](../../app.js).

### Declarative source traces

**Bistro.** The form pairs `toolname` with `tooldescription` and named, described fields. Query parameters switch autosubmit, cross-document navigation, or imperative conversion. The conversion obtains the declarative descriptor, removes its attributes, waits for `toolchange`, then registers the same name; this prevents asynchronous duplicate registration. Validation returns field errors to agent-invoked submissions with `respondWith`. Non-autosubmit imperative execution waits for the human form submit. Cross-document imperative execution requests an invocation token when that interface is present. These are source-version behaviors; that invocation-token shape must not be assumed available in the current prototype's native callback. [Form markup](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/demos/french-bistro/index.html#L30-L130); [variant and conversion code, lines 14–98](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/demos/french-bistro/script.js#L14-L98); [submission handling, lines 130–162](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/demos/french-bistro/script.js#L130-L162).

**Order tracking.** `get_order_status` autosubmits a GET form into `history.html`; `initiate_return` autosubmits another GET form to `result.html`. Query parameters carry demo inputs and the next document displays simulated outcomes. This demonstrates document-scoped tools and navigation continuity, not backend order lookup, authenticated returns, or an authorization policy. Its autosubmit choice is not a universal policy for consequential actions. The prototype continues to approve local writes and always confirm deletion/review transitions according to its own rules. [Status form](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/demos/order-tracking/index.html#L28-L40); [return form](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/demos/order-tracking/history.html#L57-L83).

### Complex UI lifecycle traces

**Flight search.** The search component exposes `searchFlights`; the results component exposes all four tools. Calls dispatch a request-ID-bearing event and wait for a matching UI completion event, with a five-second timeout and listener removal. Current flights are maintained for `listFlights`; filters update visible results and route changes reset constraints. This is stronger than announcing success immediately after dispatch, but remains React state synchronization rather than durable storage. IATA validation returns `ERROR:` strings, while the completion helper rejects on timeout. Static travel fixtures call `filterFlights`; live source calls **`setFilters`**. The source also declares `readOnlyHint: false` for mutations, contrary to the bundled skill's omission convention. Therefore the source, fixture, and guidance are not interchangeable contracts. [Event acknowledgement](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/demos/react-flightsearch/src/webmcp.ts#L3-L31); [results registration/state](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/demos/react-flightsearch/src/components/FlightResults.tsx#L46-L102); [travel fixture schema](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/webmcp-evals/examples/travel/schema.json).

**Hotel chain.** Layout tools maintain booking details while navigating; results tools modify filters and read the resulting hotel list. Details exposes `start_booking`, which only opens the form. `complete_booking` is declarative and omits autosubmit, supporting a human review boundary. Its submit handler validates and then displays a simulated reservation-confirmed screen. The included simulations distinguish preparing a form from confirming, demand preservation of trip details, abandon obsolete constraints, and reject a near match when no exact hotel exists. Navigation/result callbacks returning success do not prove the browser has rendered all new state or performed a durable booking. [Layout](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/demos/hotel-chain/src/components/Layout.tsx#L18-L84); [results](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/demos/hotel-chain/src/pages/SearchResults.tsx#L35-L82); [form and confirmation](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/demos/hotel-chain/src/pages/Booking.tsx#L58-L121).

**Ticket booking.** Location validates a city; querying returns structured movie/showtime data; selection verifies movie, date, and time before opening checkout. ## Shared helpers and native availability

The shared **polyfill** is an unversioned source file at the repository pin, not evidence of a shipping browser feature. It returns early when `window.document.modelContext` exists; otherwise it implements an EventTarget-based context, registers imperative callbacks, derives tools from forms, and installs **`document.modelContext`**. It also emulates tool CSS pseudo-classes and messaging between windows. Its `__webmcp_registered_tools` map, mutation observers, same-origin access, postMessage bridge, timeout behavior, and compatibility fallback for stringified inputs are implementation choices. Do not confuse them with normative platform enforcement. [Initialization](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/demos/shared/webmcp-polyfill.js#L6-L19); [context installation and messaging](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/demos/shared/webmcp-polyfill.js#L593-L664); [declarative changes](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/demos/shared/webmcp-polyfill.js#L667-L713).

The prototype must retain its **native Prompt API plus native WebMCP startup gate**. Loading this polyfill would make a presence/method check pass on a browser lacking native WebMCP, invalidating the experiment's purpose. The namespace is `document.modelContext`, not `navigator.modelContext`. Polyfill success does not prove native discovery, callback serialization, iframe policy, origin handling, cancellation, declarative execution, or any Chrome version claim. The current imperative chapter covers the native version/draft distinctions; the demo comments' string-input retry is source compatibility history, not permission to broaden the prototype's API assumptions. [Prototype gate and registration](../../app.js); [native API research](webmcp-imperative-api.md).

The separate shared **batch helper** registers `execute_batch`, resolves `$ref:stepId.property` from earlier results, and runs calls sequentially. It stops on a thrown error, but a resolved failure payload is recorded as success unless a consumer adds semantic checking. It is not an atomic transaction, approval system, replay guard, or rollback mechanism. The prototype already commits capture/organization batches in a single IndexedDB transaction, making those domain workflows a better fit than adopting a generic batch executor. [Batch helper, lines 6–120](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/demos/shared/webmcp-batch.js#L6-L120); [workflow contracts](../../workspace.js); [transaction/harness evidence](../harness.md).

## WebMCP Evals: what each mode measures

This package is a **developer CLI**, requiring Node/TypeScript dependencies and build/published-package tooling. It is not the local Chrome Prompt API. Its five commands have distinct claims. | Mode | Inputs and actual execution | What a pass can establish |
| --- | --- | --- |
| `local` | Static `schema.json`, `evals.json`, selected model backend; Vercel can loop over mock tool results | Selection/arguments/trajectory under supplied schemas and mock state; no page, storage, permission, or native-browser proof |
| `browser` | Live URL, Puppeteer page WebMCP registry, model backend | Expected tool calls/results on that live page under that backend; still not this app's local Prompt API |

### Test DSL and scoring semantics

An eval is an array entry with optional `name`, authored `messages`, and `expectedCall`. Message discriminants are **`message`**, **`functioncall`**, and **`functionresponse`**. Plain messages carry `content`; function calls carry `name`/`arguments`; responses carry `name`/`response`. Expected leaves use `functionName`, optional `arguments`, optional expected `result`, optional local-only `mockOutput`, and optional `optional:true`. Ordered/unordered groups can nest. Schema files use `{tools:[{name,description,inputSchema,...}]}`; runtime mapping renames `name` to `functionName` and `inputSchema` to `parameters`. [Types, lines 8–61](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/webmcp-evals/src/types/evals.ts#L8-L61); [message/tool mappers](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/webmcp-evals/src/evaluator/mappers.ts#L10-L117).

Matcher details matter when interpreting a reported pass:

- Primitive arguments compare exactly. Objects match **subsets**: all expected keys must exist and match, but extra actual keys are accepted. Arrays require equal length and positional matches.
- `$pattern`, `$contains`, `$gt`, `$gte`, `$lt`, `$lte`, `$type`, and `$any` constrain values. Multiple constraints are conjunctive; `$any` does not enforce content. Regex strings support selected leading inline JS flags; invalid/unsupported patterns can produce evaluation errors.
- Omitted/null expected arguments impose no argument constraint. Optional expected calls may be absent without pass/fail rows; if present, they are matched. Unordered matching handles overlapping constraints; nested unordered groups have a fifteen-node size limit.
- Missing required calls fail. Extra actual calls fail. `expectedCall:null` or an empty expected list allows no calls; any actual call fails. **No calls can pass while the model falsely claims that a write happened**, because ordinary trajectory matching does not grade final prose.

[Argument matcher, lines 16–79 and 141–196](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/webmcp-evals/src/matcher.ts#L16-L79); [trajectory matcher, lines 298–385](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/webmcp-evals/src/utils.ts#L298-L385).

Wrong arguments can receive a plausible successful mock; the separate trajectory matcher must still fail them. This tests reasoning over scripted outputs, not actual business validation. The Vercel schema adapter recursively **removes `oneOf` and `anyOf`** before declaring provider tools, so schema conversion cannot establish exclusive branches or full JSON Schema validation. Current native WebMCP also does not replace the prototype's callback validators. ### Smoke execution and failure limits

Smoke compiles required calls before starting; optional calls are skipped, and unordered groups execute in authored order. Calls need an argument object. The source converts constraints into sample arguments: `$contains` becomes its operand, numeric inequalities become the threshold itself, regexes are heuristically transformed, types become sample values, and `$any` becomes `sample`. **That is not semantic satisfiability**: for example, `$gt:10` becomes `10`, which does not satisfy the authored strict inequality. Prefer explicitly authored concrete smoke inputs. README language about constrained smoke inputs should be interpreted against this implementation. [Compiler and concretization, lines 72–185](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/webmcp-evals/src/evaluator/smokeEvaluator.ts#L72-L185).

Each case starts at the target URL and stops at the first unavailable tool, timeout, execution error, or recognized payload failure. Discovery can poll for up to five seconds after navigation. Default navigation/step timeout is thirty seconds. A transport success is inspected for `success:false`, `isError:true`, nonempty string `error`, or an `Error...` string/JSON equivalent. **`ok:false` by itself, `{status:'error'}`, field-error arrays, and “Invalid...” strings are not comprehensively classified by that detector**. Thus direct reuse against this app needs an explicit local result adapter and state assertions. [Smoke runner, lines 220–365](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/webmcp-evals/src/evaluator/smokeEvaluator.ts#L220-L365); [shared payload detector, lines 99–124](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/webmcp-evals/src/simulate/toolSequence.ts#L99-L124).

### Simulation DSL, semantic judgment, and final-state checks

A simulation provides **exactly one of `userMessage` or `userScenario`**, plus DOM assertions, prose `successCriteria`, or both. Direct messages avoid a user model; simulated scenarios may run multiple turns. Setup is a concrete sequence run before the agent and reported separately; it cannot be credited as agent work. Cases can override whole-conversation `maxDurationMs`; CLI budgets bound turns, agent steps, and navigation/setup/judge requests. The strict loader rejects wrong/unused keys and malformed assertion shapes before execution. [Simulation types](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/webmcp-evals/src/types/simulations.ts#L6-L123); [loader validation](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/webmcp-evals/src/simulate/loadSimulations.ts#L206-L307).

DOM assertions measure selector existence, count, trimmed first-element text, or first-element attribute value. Missing selectors yield false/zero/null according to the assertion. A deterministic mismatch fails before judgment; an assertion evaluation error is an error. Passing DOM-only cases need no judge. Prose criteria invoke a separate judge with transcript/tool evidence; empty evidence or reasoning is rejected. Exhausting a configured budget can still yield a judged pass if the intended outcome is proven, while an execution crash is an error. Setup failure prevents the conversation/judge from starting. None of this makes the judge infallible. [DOM evaluator](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/webmcp-evals/src/simulate/domAssertions.ts); [simulation hard gate, lines 234–387](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/webmcp-evals/src/evaluator/simulationEvaluator.ts#L234-L387); [judge audit checks, lines 144–184](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/webmcp-evals/src/simulate/judge.ts#L144-L184).

The strongest examples specify **outcomes plus forbidden shortcuts**. Pizza revision must keep existing mushrooms/sauce, remove corn, change style, and generate the share link after edits; resetting is failure. Hotel preparation must retain dates/guests and leave the form for user confirmation; a confirmed reservation is failure. Impossible Paris criteria require an honest no-match answer without presenting near matches. These map naturally to preserving Task fields, avoiding unrequested review advancement, and truthful receipts. [Pizza simulations](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/webmcp-evals/examples/pizza-maker/simulations.json); [hotel simulations](https://github.com/GoogleChromeLabs/webmcp-tools/blob/04732fb849ab5eff0cd8d13c6f153e26ebb7bcad/webmcp-evals/examples/hotel-chain/simulations.json).

## Proposed browser-only evaluation for this prototype

The current deterministic tests exercise scripted model decisions through production callbacks, DOM, permissions, and real IndexedDB. They establish application invariants. The documented real Chrome weekly walkthrough separately observed pre-dispatch native inference failures, wrong operation selection, title/context invention, repeated proposals, clarifications/denials, and retained receipts after Stop or later failure. The assisted eleven-step completion does not establish autonomous reliability. [Harness evidence](../harness.md), [weekly-review evidence](../weekly-review.md), [natural-language review](../natural-language-review.md).

The useful adaptation is an **optional local developer evaluation page/diagnostic mode** using actual `LanguageModel` sessions and native own-page WebMCP. This is a proposal only. It would retain the startup/model-download consent, show every write plan, and use explicitly synthetic isolated records. No cloud provider, server, build step, generic JavaScript tool, or polyfill is needed. Cases should use the production routing, projection, validators, approvals, callback execution, persistence, and receipt path; replacing those with ideal mocks would conceal the observed failures.

Measure three layers separately:

1. **Deterministic contract checks:** schema/callback rejection, record identity, exact title preservation where promised, exclusive destinations, atomicity, stale approvals, cancellation, deletion confirmation, no unsolicited review transition, and persistence after reload. Existing fixtures remain the appropriate source of reproducible pass/fail evidence.
2. **Actual local-model task outcomes:** independent fresh-case requests and continued dialogues, capturing chosen operation, proposed arguments, tool catalog/version, clarification, permission decision, actual calls/results, and before/after IndexedDB snapshots. Compare native typed tool use and constrained JSON bridge as separate configurations; record whether fallback occurred.
