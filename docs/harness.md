# Local model/tool harness

Updated **2026-10-12**. The v2 harness implements the [agreed design](harness-design-v2.md) and [implementation plan](harness-implementation-plan-v2.md). The app uses relative ES modules, native Chrome APIs and IndexedDB v2, with no build, backend, dependency installation or platform polyfill. See [implementation and fixture evidence](harness-v2-implementation.md) and the separately recorded [actual Chrome trial](harness-v2-trial.md).

## Preparation and proposal modes

Startup separately checks secure context, required Prompt API/WebMCP methods, text/English availability, text session creation, storage, and registration/discovery of all seventeen own-page tools. Ready appears only after those required layers succeed. Existing storage is opened; stores are created/upgraded only on a version change. Missing APIs open the visible Chrome setup instructions. Invalid or unavailable download progress is indeterminate; a reported 100% says preparation is still underway until create resolves. Cancel/retry discard late sessions and preserve saved records.

The prepared base is text-only. **Constrained JSON bridge** is the default, including when typed native constructors exist. The current human request first becomes a finite plan. Recognized intent anchors select a constrained operation; less explicit actionable wording uses current-only model routing. The bridge infers only the current step's arguments, or a bounded tool-free reply. Each bridge inference uses a disposable worker cloned from the prepared base where supported. Typed native proposals remain optional and execute the same registered native WebMCP callbacks.

Tools & diagnostics offers **Test native tool calls**, **Use native proposals**, and **Use JSON proposals**. A native probe is disabled when typed interfaces are absent. The user-gesture canary checks full options availability, a one-tool native session, exactly one `list_attributes({})` call, actual own-page invocation, correlated feedback, and final text. Its scoped Allow once card always appears, even with an existing root chat grant; it cannot grant chat authority. Canary limits are three inference stages, one read dispatch and thirty active seconds. Constructor presence, ordinary prose, or availability alone cannot pass it. Reload/configuration/native contract failures invalidate native readiness.

Changing transport or catalog is idle-only, including while a continuation is pending. Native worker-creation failure chooses the bridge before proposals. Only a failed first native inference on a fresh request, without finalized calls, dispatch, cancellation, AbortError, continuation or uncertain effect, permits one bridge fallback. Both attempts count in the same run. No dispatched write is automatically replayed.

## Host lifecycle and saved facts

`agent-host.js` owns ordered events, run/round/call/child identities, serial dispatch, worker ownership, continuation and cancellation. Defaults are **24 inference stages, 18 dispatch attempts, 180 active seconds, and six dispatches per segment**. Every route, argument, reply, native proposal/feedback, failure and fallback counts. Permission and draft-decision waits pause active time. Continue resets only the segment count and preserves the original request, aliases, receipts, signatures, outcomes and review boundary. Exhausted totals hide Continue. A fresh human request closes an abandoned continuation.

At most a prepared base plus one owned worker is live. The host prevents overlapping inference across runs and destroys cancelled or late-created workers. A signal-ignoring operation can temporarily block a new inference rather than overlap it. Stop aborts permission, inference, owned worker and child work; it does not undo durable transactions.

A private one-use own-dispatch handoff uses a cryptographically random transport token plus the validated call signature to capture the host handle at callback entry, before any await. A matching signature alone cannot prove the invocation. The token is absent from public/model schemas, stripped before normal validation/permission/activity, never exported/logged by the app, and expires on Stop/finally. WebMCP deserializes inputs and supplies a distinct provider signal, so neither object nor caller-signal identity is used. This is correlation within the trusted host page, not isolation against same-privilege page scripts that can intercept transport and already access storage. External WebMCP callbacks and manual writes receive no root handle. Callback arguments are copied/frozen before approval. Immediately after `mutate()` or `transitionReview()` resolves, the callback records immutable effect evidence before memory, rendering, navigation, BroadcastChannel, status or cancellation checks. This covers generic create/update/attributes/parent/delete, all atomic workflows and review progress. Deleted titles/count remain available for factual summaries.

That admitted effect handoff survives Stop while the run retains cancellation as its terminal reason. A matching receipt also proves a committed write after callback/render/transport failure. The harness reports that saved result and stops later dispatch. Without a receipt, a lost dispatched-write response is uncertain and requires inspection/new human instruction. Transport results are parsed once and must be exactly one success/error envelope; arbitrary nested JSON is not unwrapped.

Repeat signatures equate omitted and empty `capture_tasks.context`, matching its domain default without changing approved callback arguments. Nonempty capture contexts remain distinct; update/patch omission still differs from an explicit context clear.

The complete native batch is validated before its first call: allowed catalog, argument choices, the 32-part bound and unique unambiguous correlation. `callId` and observed `callID` are transport identity only; supplying both is rejected. A solitary empty ID remains an explicitly recorded compatibility case. Every admitted sibling settles, including skipped calls after denial/error/clarification/review transition/budget/Stop. Correlated feedback cannot reopen dispatch. Repeated operations and item/review boundaries preserve distinct remaining item work in a finalized batch while suppressing the blocked operation.

## Context, catalogs and Inbox

Trusted UI-generated guidance after Start, Complete step and Resume renders the current step's trusted instruction and focused question directly. It uses zero model inference or tools across Standard/Full and both proposal adapters. The UI already selected the correct view, so this cannot invent a context filter or mutate records through a chat grant. A fresh human chat request is planned independently.

`agent-context.js` builds stage projections from current authoritative facts. Action routing and argument stages exclude conversation history. Pure helpers retain bounded whole-history support for future conversational experiments; history cannot create effect authority. Current exact intent, titles/negation, review boundary, verified current-run receipts and closed readable choices remain protected. Route context has names/descriptions, arguments have only the selected schema, and replies have verified results. Stored descriptions, historical prompts and tool/report text cannot grant authority.

The Standard profile selects thirteen tools: five semantic item workflows, `weekly_review`, `list_items`, `read_item`, `show_view`, `create_item`, `update_item`, `delete_item`, and `ask_user`. Full also offers `list_attributes`, `read_attribute`, `update_attribute`, and `set_parent`. All seventeen public tools remain registered/inspectable; model tools with no applicable choices are omitted. Readable aliases are frozen through Continue. New records enter choices on a fresh request, duplicate titles clarify, and referenced records outside the selected view remain available. Strong callback schemas stay separate from model/decoder projections. Explicit Area and named-container additions use constrained title/type/status/parent creation; see [usability improvements](usability-improvements.md).

The named default **Chromium compatibility** decoder projection removes previously rejected keywords and redundant parameter-description metadata. **Retain parameter descriptions** is available for explicit comparisons in both adapters. The literal application property `description` always survives, along with exact enums, omitted-field meanings and callback exclusivity checks. A single explicit current-human `new Project named/called/titled` destination narrows `organize_tasks` to its literal `newProjectTitle` enum and removes the existing-parent branch. Quoted names preserve punctuation/escapes and allow a clearly separated following sentence/semicolon instruction; conservative unquoted extraction requires an unambiguous sentence suffix and rejects embedded instruction sentences. This constrains arguments and does not select a route or draw authority from stored DATA. `show_view.context` offers existing readable workspace context labels, their @tags, matching literal request substrings, and empty, preserving ordinary domain labels while blocking invented filter garbage. Native description-profile compatibility still requires a canary on the actual browser.

At the underlying catalog level, for `organize_tasks`, `complete_task` and `set_task_status`, a current human request naming known Tasks narrows the title enums to those names. Literal matches are case-insensitive with word boundaries; the longest overlapping title wins, and distinct named Tasks form a union for compound work. Records sharing a title remain in the planner's ambiguity checks. Unknown/unmatched/vague wording retains the original choices. Lexical broad scope such as all/each/every/remaining/other tasks, all of them, the rest or everything retains unrestricted choices; this fallback does not authorize that scope and may also occur in a negated phrase such as leave all other tasks unchanged.

Recognized exact capture literals supply additional choice closure. Unknown/new captured names cannot select freshly created records during this run, so a literal-only capture hides existing completion/status/organization tools when it names no existing Task elsewhere. Known existing names in compound work remain available; exact existing captured names also remain available. Literal names are masked during other-name matching, so a short existing title inside a new longer capture is not treated as a separate requested Task. Broad scope outside those literals retains the original choices.

The underlying focus guard applies to title-workflow fields and validates proposals in both adapters before dispatch, including later rounds under a chat grant. It is not a complete intent/permission policy: generic primitive target references, free new titles, action/status semantics, incidental named mentions and unmatched/broad lexical fallbacks retain their existing boundaries. The model can still make an unrelated proposal through those surfaces, so successful fixture focus checks must not be described as a general intent firewall.

`inInbox()` is shared by UI, queries and specialist: unfinished parentless Tasks. Use `list_items({scope:"inbox"})` for that domain scope. `parentId:null` remains a generic root-record query, including containers/completed records. Filters combine conjunctively, and responses report scope/filters/total/truncation.

Where supported, every stage measures its actual input/options and records current usage/window. Input plus existing session usage must leave at least 25% reserve. Trim complete history and optional visible/descriptive facts, then remeasure the actual trimmed input; no JSON-size ratio is treated as token proof. The measured reserve check applies to every actual input shape, including plain canary text and native typed tool-response feedback; a blocked feedback stage preserves prior receipts and does not prompt or dispatch again. Missing/unusable usage is unknown. A 48,000-character input-plus-schema fallback guard still applies. Protected overflow asks for narrowing before dispatch. `contextoverflow` records failure and disposes the worker without replay; a new bounded request starts at a closed boundary. Result projection retains the 8,000-character ceiling with truncation metadata; full arguments/results stay in activity.

Verified receipts produce saved summaries. A mixed write/read turn also displays the guarded answer to its requested successful read. The final prose guard remains active even with receipts; an unsupported extra completion claim is withheld with a message preserving the saved facts and the attempt is classified unfulfilled. A conservative guard replaces definite unverified first-person/write completion claims with factual no-change text and marks the attempt unfulfilled. It preserves factual status phrases such as completed Tasks. This is a heuristic, not a guarantee of correct model reasoning. A narrow greeting-only route offers respond. Recognized action steps infer their narrowed arguments without another route stage; unknown actionable wording retains current-only model routing. A strictly empty mind-dump introduction is attached to its actual capture; header-only messages ask for thoughts, while distinct captures stay separate. A verified success or no-op fulfills the step once and closes it; no post-success rerouting is allowed. Requested reads can produce guarded tool-free answers.

## Current request policy

`request-policy.js` forms at most eighteen finite requested steps, preserving the existing six-dispatch segment and shared totals. It masks literal strings and known record labels for operation classification. Task completion, independently requested review progress, organization, shopping, captures, generic creates/reads and exact context edits use separate semantic steps. Contradictory same-field changes and unparsed compound actions clarify before writes. Item changes still defer compounded review control to a fresh human instruction; preserving an existing Task status is not a write.

Immediate current-turn pronouns can reuse an unambiguous preceding Task subject; repeated identical effects collapse before inference. Preservation, negation and intervening unrelated clauses clear that subject. Supplied captures followed by “Capture it/them” remain one capture, while completed mind-dump narration creates no new capture. Positive new-Project syntax is classified outside literal and known-name spans, so an existing Project containing “new” stays an existing destination. No whole-message new-title preference overrides this planned branch.

A context-only edit exposes only `update_item`, one readable target and `patch.context`. The exact literal is a singleton enum and callback-bound host constraint: case, `@`, slash, spaces and an explicit empty string survive unchanged. Other patch keys and substituted values are rejected even under chat grants. If ID projection changes a literal, the model receives a per-slot sentinel choice; the host restores the original validated string after equality checks. Approval shows exact old/new values. Quoted context values cannot become additional targets or operation instructions.

No-tools/ask-before-change and ambiguous destinations produce grounded questions without inference or dispatch. Only a positively requested move with unique Task choices creates a private pending destination descriptor. A strict fresh answer chooses a unique, unchanged Project or Inbox, then uses normal permissions. Negation, changed/deleted/duplicate options and unrelated requests cannot revive or expand that authority. Parent qualifiers distinguish duplicate targets where the chosen primitive supports them; ambiguous workflow title choices still clarify.

Aliases remain frozen throughout Continue. When declared later steps change independent fields on the same Task, only immutable records in this run's committed receipts may update those expected revisions. Fresh records must equal those revisions before later dispatch; original reference snapshots are used only for compatibility after that check. External changes stay stale. Review control binds the displayed original saved review position: admission refreshes changed progress and asks a new confirmation, callback entry checks the saved position before approval, and the existing transaction fence checks again at commit.

This policy is a bounded prototype intent guard, not a complete English parser. Explicit context values need a clear quoted boundary or a single unquoted @tag; vague/unparsed compounds may ask the user to separate requests. Generic primitives and unmatched action wording still require model interpretation and ordinary human approvals. Strong plans close fulfilled operations, rather than inviting the model to invent another operation from earlier conversation.

## Requested next-action reviewer

Inbox and selected Project headers offer **Ask reviewer** with a visible human scope instruction. Explicit chat reviewer requests are admitted only for unambiguous Inbox/selected Project scope. Ordinary guidance/model prose does not admit a child.

The host admits one child per run, freezes scope membership/revision, and supplies at most forty records/16,000 serialized characters with omissions. Project scope includes its Project and immediate Tasks; Inbox uses the shared predicate. Empty/unrepresentable snapshots return a no-change explanation without constructing an impossible enum grammar.

The reviewer uses one fresh text-only session, no tool declarations/dispatcher/grant, no transcript clone, no navigation/review/approval interface and no child spawning. Creation is active work; its single inference counts against the root's shared totals and has a thirty-second deadline, with no retry. It returns exactly observations/suggestions/questions/limitations, each array bounded to ten, each text to 400 characters, report to 6,000 characters, and references to the admitted readable snapshot. Actor/identity/extra fields are rejected.

Before accepting, the host checks lineage, cancellation, report shape/references, current scope membership and the full revision signature including omitted records. Stale, malformed, late, timeout or budget failures cause no page dispatch/effect. Accepted advice is rendered as text with evidence labels under **Reviewer suggestions; no changes made**. Advice cannot approve or execute a suggested change: a new human root instruction uses ordinary gates.

## Persistence and diagnostics

Both decoder profiles omit unsupported `uniqueItems`, `oneOf`, `not` and `minProperties` from model schemas. Public callback schemas retain their full validation, and ask_user's distinct options are also checked explicitly by the host. The real Chrome follow-up exposed the uniqueItems incompatibility; see [usability evidence](usability-improvements.md).

In-memory pending clarification choices are discarded by Stop, New chat, reload or an unrelated fresh request; stored chat cannot reconstruct their authority. Items, preferences, history and saved/paused review position remain in existing IndexedDB stores. Reload discards chat-wide grants, continuation, pending calls/approvals/questions, native readiness, events and child execution; it never resumes work from history. Explicit per-tool Always allow choices persist in preferences, are read at callback entry and revalidated before their operation, and can be revoked individually or together in Tools. Deletion always needs separate confirmation. A chat-wide grant alone does not bypass fresh review complete/skip approval; an explicitly remembered weekly_review grant does. There is no store/version migration or durable replay guarantee.

`ask_user` returns a visible button or custom text answer to the model, separately from permission. Question waits pause active time and end on Stop, Escape or Cancel. A native question before a remaining declared step leaves that step pending with its original constraints; question/write native batches are rejected before dispatch, negative answers stop the action, and at most three questions fit within the normal shared budget. The bridge supports question-only and conversational turns while recognized actions retain direct narrowed argument inference. Fulfilled turns do not discover extra question work. Host clarification questions can offer grounded buttons that submit fresh human answers.

The in-memory journal retains the latest 500 events; active/admitted outcomes/receipts remain separately available. Settled quiescent run diagnostics are bounded to fifty; admitted callbacks with outstanding invocations retain their receipt capability. Tools exposes dated pass/fail/unsupported/unknown layers, stage/name/message errors, input usage or unknown, actual selected transport and optional manually supplied channel/build/flag/model notes. **Download diagnostic JSON** is user initiated and local; it can include local item text. No automatic export or upload occurs.

Service-worker shell cache v8 contains the agent modules and request-policy module and continues same-origin/subpath handling, offline navigation, unrelated-cache preservation and missing-asset failures. Installation fetches shell Requests with `cache:reload`; online navigation/shell fetches use `cache:no-cache`, so still-fresh HTTP cache entries cannot mask changed deployment bytes. A max-age=3600 old-v5→new-v8 regression checks actual executed/cached JavaScript and navigation HTML after a normal reload and offline. Existing eleven-step weekly-review controls, atomic workflow planning, delete-subtree confirmation and transaction revalidation remain intact.
